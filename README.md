# 公交接驳满意度调查 · 两版均分差值复核页

更正后的满意度调查需要估计「更正表均分 − 原表均分」及其抽样波动。本服务提供一个
Flask 网页：上传原表 CSV → 入库（SQLite 原样保留）→ 按户补录 / 改分 / 移除 →
固定种子的 1000 轮泊松自助 → 展示未加权均分差、有效轮数与轮差值的 2.5% / 97.5% 分位。

## 一键启动

```bash
docker compose up --build
# 浏览器打开 http://localhost:8000
```

- 数据库落在命名卷 `survey-data`（容器内 `/data/survey.db`），容器重建后数据仍在。
- 生产环境请修改 `docker-compose.yml` 中的 `SECRET_KEY`。
- 本地无 Docker 时：`pip install -r requirements.txt` 后
  `gunicorn --bind 0.0.0.0:8000 --workers 1 --threads 4 wsgi:app`
  （SQLite + 单进程多线程；每请求独立连接）。

## CSV 格式

UTF-8 文本（允许 BOM），每行两列：`住户号,评分`。

- 住户号：非空、全表唯一；
- 评分：0～10 的整数；
- 首行若是表头（第二列不是整数）会自动识别并跳过；空行忽略；
- 任一记录非法则整次上传被拒绝，数据库不做任何改动。

## 页面操作与展示

1. **上传原表**：原表写入 `original_scores` 后不再被任何功能修改；更正表
   `corrected_scores` 初始化为完全相同的副本。
   - **首次上传**：全部住户生成抽样权重。
   - **重传（增量）**：以当前已提交的原表和它的轮次汇总为基准，只为**新增、
     移除或评分有变**的住户生成权重，其余住户沿用已有权重；仅调整行序时
     生成权重的户数为 **0**。原表汇总按变更户的增量累加，结果与全量重算逐位一致。
   - 页面显示本次上传方式（全量/增量）和**本次生成权重的户数**。
   - **并发保护**：页面在打开时记录基准（代数 + 内容指纹）。若从取基准到提交
     之间已有另一笔原表上传先入库，本次整体退回并提示重新上传，即使对方传的
     是相同内容。同期的人工更正不影响上传生效；上传成功后更正表从新原表
     重新初始化。
   - 校验失败或写库失败时事务回滚，继续使用现行数据。
      - 原表汇总总量（`orig_weight_total` / `orig_weighted_sum`）随每次上传与更正
     写入 `meta`；增量重传前会核对原表、更正表与汇总是否一致，不一致时拒绝增量，
     需勾选「强制全量重算」修复。
   - 旧库无需迁移：首次读取时自动补齐基准元数据（`orig_fingerprint` /
     `upload_generation` / 汇总总量等），之后即可增量重传。
2. **按户更正**：输入住户号，选择「补录 / 改分 / 移除」（移除不需要评分）。
   另有单户查询（只返回该户两版评分，不读取其他户明细）和「重置更正表为原表」。
3. **估计结果**（只读 `meta` 与两张轮次汇总表，不碰住户明细表）：
   - 两表户数与未加权均分；
   - 未加权均分差（更正 − 原）；
   - 有效轮数 / 1000，以及被跳过的轮数（任一侧权重合计为 0 即跳过）；
   - 轮差值的 2.5% 与 97.5% 分位（type-7 线性插值，与 numpy 默认定义一致）；
   - 无法计算时显示明确原因（未上传、更正表为空、全部轮次权重合计为零等）。

## 自助抽样方法（与需求逐条对应）

- 固定种子（`app/bootstrap.py` 中 `MASTER_SEED = 20261123`），共 **1000 轮**；
- 每轮每户独立抽取均值为 1 的泊松权重 `Pois(1)`（Knuth 算法）；
- 权重是 `(种子, 轮次, 住户号)` 的确定性函数（BLAKE2b 取 64 位 → SplitMix64），
  因此：
  - **同户在两表共用同一权重**；
  - 其他住户的新增、删除、重排都**不会改变该户的权重**（权重不依赖行序或邻户）；
  - 重复运行结果逐位可复现；
- 每轮计算
  `d_r = 更正加权均分_r − 原表加权均分_r = Σw·s/Σw（更正） − Σw·s/Σw（原）`，
  任一侧 `Σw = 0` 时该轮跳过。

## 存储与事务设计

| 表 | 内容 |
| --- | --- |
| `original_scores` | 原表户号 + 评分，上传后只增不改（重新上传时整体替换） |
| `corrected_scores` | 更正表户号 + 评分，按户编辑 |
| `orig_rounds` / `corr_rounds` | 每轮的权重合计 `weight_total` 与加权评分合计 `weighted_sum`（各 1000 行） |
| `meta` | 两表户数、评分合计、上传基准（内容指纹 + 代数）、原表汇总总量、最近一次上传方式与生成权重的户数 |

- 每次更正只重算**该户**的 1000 个轮次贡献（`UPDATE ... ±`），其余户数据不读取；
- 更正表明细与 `corr_rounds` 汇总在**同一个 SQLite 事务**内提交，任何失败都回滚，
  页面继续展示上一版结果并提示原因；
- 增量上传的权重生成在**事务外**完成（因此计算期间查询与按户更正照常可用），
  写库时用 `BEGIN IMMEDIATE` 开启事务，并在事务内复核基准代数/指纹，不一致即
  回滚并提示重传；
- 原表、更正表（从新原表重新初始化）与两张轮次汇总在**同一个事务**内一起生效；
- 使用 WAL 模式，读取不会被上传写入阻塞；gunicorn 以 2 个 worker 运行，长耗时的
  权重生成不会拖慢另一个 worker 上的查询/更正；
- 上传页提供「强制全量重算」选项（维护用），结果与增量逐位一致，可用于疑似汇总
  异常时重建；
- 分析查询仅访问汇总表与 `meta`，满足「查询只读汇总」。

## 目录结构

```
app/
  __init__.py      Flask 工厂与路由（上传 / 更正 / 重置 / 查询 / 健康检查）
  bootstrap.py     固定种子确定性泊松权重
  csv_io.py        CSV 解析与校验
  db.py            SQLite 建表、入库、按户更正事务、重置
  stats.py         只读汇总分析与 type-7 分位
  templates/index.html
tests/             unittest 测试（36 个，含端到端 HTTP 流程与增量上传/并发冲突）
Dockerfile / docker-compose.yml / wsgi.py / requirements.txt
```

## 测试

```bash
python -m unittest discover -s tests -v
```

覆盖：权重确定性与「邻户增删不影响本户」、Pois(1) 经验分布、分位插值、
汇总与逐户重算一致、原表只读、更正事务失败回滚、零权重轮跳过、空表原因提示、
完整 Flask 上传/更正/查询/重置流程，以及增量上传（只重算变更户、结果与全量重算

写库中途异常回滚保留现行数据、强制全量重算。

## 演示数据

`samples/` 下有两份可直接在网页试传的 CSV：

- `samples/original.csv`：1200 户的首次上传原表；
- `samples/reupload_few_changes.csv`：在它基础上改了 3 户评分、移除 2 户、新增
  1 户，并把全部行打乱（用于演示只有 6 户生成权重）。

先上传 `original.csv`，再在同一页面（不要刷新丢失基准）上传
`reupload_few_changes.csv`，页面会显示「本次为 6 户生成抽样权重」；把同一份文件
的行序反转后再传，则显示「本次为 0 户生成抽样权重」。

## 性能参考（实测，Python 3.11）

| 场景 | 耗时 |
| --- | --- |
| 1200 户首次上传（全量权重 + 两表汇总初始化） | 约 10 s |
| 1200 户中 6 户变更后重传（增量） | 约 0.13 s |
| 3000 户全量上传 | 约 75 s |
| 单户补录 / 改分 / 移除 | 约 0.03 s |
| 分析页查询 | 约 0.007 s |

gunicorn 超时设为 120 s；更大规模数据集可在 compose 中调大 `--timeout`。
